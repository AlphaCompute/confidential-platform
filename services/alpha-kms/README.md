# alpha-kms

The key broker of the trust plane: seven tables, seventeen `/v1` routes on one TLS port (`:8443`, TLS 1.3, `X25519MLKEM768`), plus `GET /healthz` (process only) and `GET /ready` (database checked, `{"sealed": …}`; `503 {"halted": reason}` once the node has halted).

The Instance API is `POST /v1/attest/nonce`, `POST /v1/attest`, and two routes that need the Instance's leaf as a client certificate: `GET /v1/secrets/{name}` and `POST /v1/keys/derive`. The last answers `{"key"}`, 32 bytes derived from the organization's `org_key` and the leaf's App id for the requested `purpose`, the same for every Revision of the App; it is how an App holds a key no person ever sees, and nothing but an attested Instance reaches it.

`POST /v1/channel` answers an inner-channel handshake with the node's leaf and a ticket, and `PUT /v1/secrets/{name}` then takes the value either as `value` or as `sealed: {ticket, frame}`, whose plaintext begins with the signing digest of the put's payload, so a relay sees only ciphertext; any node of the deployment opens the ticket within ten minutes.

Control bodies are signed `ed25519` or `webauthn-es256`, a passkey's WebAuthn assertion over the same signing digest, accepted only on the origins and `rp_id` of the current platform document's `signer` and refused everywhere, stored signatures included, when the document has none; a passkey can be an organization's root key.

## Configuration (environment only)

| Variable | Meaning |
|---|---|
| `ALPHACOMPUTE_DATABASE_URL` | Postgres 18; the service user is a member of the `alpha_kms` role the migration creates |
| `ALPHACOMPUTE_KMS_ENDPOINTS` | comma-separated `https://…` of the KMS nodes; walked on a sealed start to `join` |
| `ALPHACOMPUTE_PCCS_URL` | PCCS for DCAP collateral, fetched per attestation |
| `ALPHACOMPUTE_PLATFORM_DOCUMENT_URL` | the release-signed platform document, fetched on start and every five minutes |
| `ALPHACOMPUTE_FORTANIX_CCM_URL` | optional `https://` endpoint of the Fortanix CCM GPU backend, which refuses every GPU until F8; unset, a `gpu_policy` listing `fortanix-ccm` refuses every GPU pod |
| `ALPHACOMPUTE_QUOTE_SOURCE` | unset or `dstack` on a prototype CVM; `coco-aa` (the CoCo attestation agent) or `coco-tsm` (configfs-tsm) on a Kata pod, as for `alpha-runtime` |
| `ALPHACOMPUTE_KMS_DEV_ROOT_KEK` | `dev-root` feature only: 64 hex digits used as the root KEK instead of the custodians' shares |

`alpha-kms migrate` applies `migrations/` (expand-only) and returns; run it as the schema owner. The service then learns what it is (`NodeGuest`): on a prototype CVM, its event log from the CCEL table and `/run/log/dstack`, whose compose-hash event is its Revision; on a Kata pod, the init-data it booted with (`/run/alpha-pod/cc_init_data`, projected from the pod's `cc_init_data` annotation), whose Revision v2 is its Revision and must name the CPU class `kata-qemu-tdx`. It generates its P-256 runtime key and X-Wing key and comes up sealed: it joins the first ready endpoint or waits for two `unseal` shares (or, on an empty database, a `bootstrap`). With the database closed (M2(a), `docs/db-volume-key.md`), custodians' share files carry the database's volume key wrapped under the root: the node unseals into a waiting phase, gives the key to the attested Postgres pod listed in the platform document's `db_revisions` (`POST /v1/node/db-key`, a nonce from `POST /v1/node/nonce`), and serves once the database answers; the pool connects lazily for that. A serving node replaces the custodians when two current ones approve (`POST /v1/node/custodians/rotate`, `GET /v1/node/custodians/rotation`; `docs/custodian-rotation.md`): a new root KEK re-wraps tenant-kek-root and the CA key, and a new data key re-encrypts every sealed row, blind index and Secret value, in one transaction; the old shares open nothing after it, and an old backup with old shares opens only that backup (plus the derived keys and the CA key, which do not rotate). `GET /v1/node/evidence` serves a prototype node's quote and event log, or a Kata node's `alphacompute-evidence/2` (its init-data included) from the same CoCo source `alpha-runtime` uses; either way the X-Wing key is bound in `report_data[32..64]`. The serving node admits a joining node, and a custodian's CLI a node it seals to, through one appraisal, `alpha_attest::node` (`docs/kata-attestation.md`, "A KMS node on Kata").

The database is an untrusted store (`docs/metadata-encryption.md`, D4). Each row keeps in the clear only random ids, the compose hash, timestamps and HMAC blind indexes; everything else is `sealed`, AES-256-GCM under keys derived from tenant-kek-root, so a sealed node reads and writes no tenant row. The audit log is a hash chain whose sealed rows authenticate everything before them; a node without keys appends only node facts, in the clear. Entering the serving phase seals any row an earlier release wrote in the clear before the node serves (unseal → the database's keys → seal → serve), and every platform tick seals stragglers and verifies the chain from where it stopped, reporting `audit_chain` on `/ready`. Each node keeps the highest audit head it has seen committed, in memory, and learns heads from the node it joins (`JoinReply.audit_head`), from its peers (`GET /v1/node/audit-head`) and from custodians' share files (`UnsealRequest.audit_floor`). A database that does not hold one (restored from an older copy, or another copy) halts the node, and so does a broken chain: `/ready` answers `503` with a fixed reason, every route outside `/v1/node/*` and every key release answers `503 halted`, and nothing more is appended until an operator restarts it.

The release key's public half is `release-key.pub`; replacing it means rebuilding the image.

The image is `images/kms/Dockerfile` (`alpha-kms`, or `alpha-kms-dev` with `--build-arg FEATURES=dev-root`), built and reproducibility-checked by `.github/workflows/release.yml`; the two nodes' compose and the operator's steps are `deploy/README.md`.

## Tests

`cargo test -p alpha-kms` runs the unit tests always and `tests/db.rs` when `DATABASE_URL` points at a Postgres the tests may `create database` in (each test makes its own). The db tests attest with real Phala quotes from `testdata/attest/*-keyed`, pinned to the capture's time, nonce key and collateral, and cover the server side of every route: bootstrap once, unseal with one and two shares, join only for an attested, listed, requesting node; the Control API's checks and idempotency; sealed puts and their refusals; attestation, release, revocation on the next call, the derived key's stability across Revisions and separation across Apps with an audit row for every refusal, re-verification of a tampered row, the anchor and chain rules, `cert_invalid` for a self-signed client certificate; the monotone platform document, a rollback refused with an audit row; and the append-only audit role.

`tests/passkey.rs`, on the same database, covers passkey signatures: a captured iCloud Keychain assertion claiming an organization, software passkeys on every Control route, attestation, secret read and key derivation, and the refusals without a signer, on a dropped origin, under another organization's key and for a stored row missing its fields.

`tests/kata.rs`, on the same database, covers Kata confidential pods (`docs/kata-attestation.md`) over synthetic quotes: Revision v2 registration, a GPU pod's and a CPU pod's leaf naming their Revision v2, evidence v2 through the route reaching DCAP, and an audit row for an unregistered or revoked Revision v2, a GPU backend the node does not run or that refuses, and a failed TD or GPU check. `tests/malicious_host.rs` is the malicious-host core suite (`docs/kata-attestation.md`): every case a hostile host can try on a Kata pod's attestation, each refused with its named reason and audit row; CI runs it as its own step.

`tests/kata_node.rs`, on the same database, covers a KMS node on Kata over synthetic quotes: its identity from CPU-class init-data, its evidence v2 served by `GET /v1/node/evidence`, genesis by three custodians through `alpha-cli`'s `verify_kata_node` and `bootstrap`, a second Kata node unsealed by two of them, a Kata node joining a prototype node (and refused, with its audit row, when its build is unlisted, listed as a prototype build, its quote binds another X-Wing key or no join was requested), evidence v2 through the join route reaching DCAP, and clients pinning the CA with both builds' Revisions.

`tests/sealed_store.rs`, on the same database, covers the store: after every route has run no tenant value is in any column of the raw tables and every plaintext column is null, while the routes still find their rows by blind index; a sealed blob flipped, moved to another row or left in the clear is refused; a node without keys writes only node facts; the audit chain breaks at a flipped, swapped, re-timed, removed or replayed row and at an edited node fact even with its link recomputed; the service role cannot rewrite a linked row and scrubs only an imported one; a broken chain halts the node (not ready, nothing released, nothing appended); and rows an earlier release wrote in the clear are sealed, and its audit rows imported, when a node unseals.

`tests/audit_rollback.rs`, on the same database, restores the database from an older, internally consistent copy (its chain verifies) and shows it refused: the serving node halts at the next request instead of releasing the copy's Secret value, and a maintenance pass finds it with no request; a joining node handed the serving node's head halts instead of serving the copy; a node halts when a peer's head, read over the pinned channel, is not in its database; and a custodian's share file carries the head across a cold start, with `--accept-audit-rollback` as the explicit way to accept a restore.

`tests/custodians.rs`, on the same database, covers custodian re-share with root rotation (`docs/custodian-rotation.md`) through `alpha-cli`'s library: two current custodians replace one and then all three, every wrapped row changes and a data key of a new epoch joins them while tenant-kek-root and the CA key keep their values, the receipt verifies against the CA and names exactly the shares; old shares, alone or beside a new one, unseal nothing while two new ones do and every sealed row and the audit chain still open; one custodian (one share sent twice, or a made-up second share) cannot rotate, nor can a sealed node be asked; a nonce not minted by the node, an expired one, a proposal for another node, with a repeated key or another format, an approval of another proposal or under the unseal info, and a replay of both approvals or of the nonce are refused; a rotation whose last write fails leaves every row byte for byte and the old shares working, and a lost reply is fetched from a node started later; a node joined before the rotation writes nothing under the replaced data key, drops it on its next pass and joins again, then verifies the chain across the rotation and runs the next rotation; and two old shares with a backup from before the rotation open that backup but no Secret, row, blind index or audit row the database holds afterwards, while two current shares open them all and an App's derived key is unchanged. `tests/kata_node.rs` rotates on a Kata node with the agent-policy baseline check.

`tests/db_volume.rs`, on the same database, covers M2(a): a sealed node refuses the volume key; a serving node gives it to the listed Postgres pod only, sealed to that pod's X-Wing key from that node, and refuses an unlisted Revision, one listed only as a KMS build, a quote over another X-Wing key or nonce, a nonce it did not mint, prototype evidence, and evidence whose DCAP fails, each with a `db.key` audit row; a node unsealed with its database closed waits, answers only the Node API, gives the key out only under a document as new as the custodians verified, then serves once the database answers and appends what it held; share files without the wrapped key leave it sealed; and genesis with the database closed writes its rows once it opens, after which two shares unseal another node.

`tests/cli.rs` drives `alpha-cli`'s library functions against the same in-process node (`crates/alpha-cli/README.md`).

Not here: the `alpha-runtime` pins, the backup/restore drill, anything that needs a live CVM with the guest agent's socket or a live Kata pod with its attestation agent (`GET /v1/node/evidence` of a prototype node, a DCAP-verified Kata node quote, a real `join` client run), and the HPKE/X-Wing known-answer tests (`alpha-crypto`).
